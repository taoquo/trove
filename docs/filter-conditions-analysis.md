# 筛选:下一个条件该是什么

这份文档回答:**书签库的「筛选条件」面板现在只有两个开关能用,下一个该加哪一个,它要花多少代价。**

分析在前,本文不改任何行为。已经存在的条件写在 `design.md` 的契约里;这里说的是还没有的东西,
以及它们各自的数据从哪来。

> **实施状态(2026-11-15)**:§4 的归档已经实现,形状与这里的建议有一处不同:它是面板里的开关,
> 不是侧栏的 scope(原因见 §4 末尾)。未读 / 已读同日实现,验收后**撤除**——自动标记、单向、
> 没有正向标志,一个从没读过的书库满屏圆点(原因见 §4 末尾的第二段)。§2、§3 的其余条件仍未做。

字段与数字来源:本仓库的模型与 SQL(`libraryquery.go`、`bookmark.go`、`bookmark_repo.go`、
`parse.go`、`migrations.go`),加上 X 的 tweet result 结构。§3 有几条无法用本仓库的代码证明,
文中写明了核对方法,没有核对的不要当成已确认的字段。

---

## 0. 结论

1. **面板的问题不是"条件少",是它只覆盖了一层。** 面板列四项,两项能用(`sidebar.go:450`);
   两项是从没实现过的占位(`sidebar.go:458`)。而在"内容是什么"这一层里,库里已经有、却筛不到的
   至少有七项(§2)。
2. **真正的空洞在状态层。** 未读与归档不是没有数据源,是没有存储:代码里两条共用一个占位字段
   (`sidebar.go:459`)。它们是稍后读的主循环,而且不该做成面板里的勾选框(§4)。
3. **内容生态里信息量最大的三项:媒体类型(数据已在)、链接域名、语言。** 后两项要动解析器,
   语言还无法回填历史数据。
4. **模型判断不要进筛选。** 主题、质量、"爆款"已经由标签与未决建议两条管线承载;放进筛选,等于让
   列表里有什么由一个看不见的分数决定(§5)。
5. **一个布尔条件要碰 18 个文件**,因为条件得同时进 `LibraryFilter`、SQL、`SavedView`、旧版导出
   和三份清单。宁可少而准(§7)。

## 1. 现状:三层条件,各在各的地方

| 层 | 条件 | 现在在哪 | 出处 |
|---|---|---|---|
| 内容 | 包含媒体、长文 | 筛选面板里两个能用的开关 | `sidebar.go:450` |
| 内容 | 未读、已归档 | 面板里两行灰字,勾不动 | `sidebar.go:458` |
| 内容 | 有未决建议 | 工具栏那个计数,不在面板 | `toolbar.go:574` |
| 来源 | 一个标签、一个作者 | 侧栏 facet 行 | `filterfacets.go:65` |
| 来源 | 全部 / 收件箱 / 某个列表 / 未归类 | scope,是导航不是条件 | `libraryquery.go:91` |
| 来源 | 收藏于最近 7 / 30 / 90 天 | 只有模型,界面上没有入口 | `libraryquery.go:24` |
| 顺序 | 五种排序,含赞数从高到低 | 工具栏排序控件 | `savedview.go:11` |

三处已经在漂移,而且都不是新问题:

- 面板手写了四个 checkbox(`sidebar.go:450`),开关表里却有三个(`filterfacets.go:85`)——
  "有未决建议"是个条件,但它不在面板里。
- `SavedView` 只存媒体与长文两个开关(`savedview.go:49`),`ApplySavedView` 也只恢复这些
  (`listsviews.go:119`)。也就是说:**已经有一个条件(未决建议)和一个维度(时间区间)存不进保存的
  视图**——存的时候丢掉,回来的时候更窄。
- `LibraryFilter` 有十一个字段(`libraryquery.go:68`),面板露出两个。

三条都指向同一个修法:面板遍历开关表,而不是自己写一遍。这样加条件是一行,漏一个也会当场显形。

## 2. 库里已经有、只是筛不到的

| 条件 | 数据在哪 | 它回答什么问题 | 代价 |
|---|---|---|---|
| 媒体类型(图 / 视频 / GIF) | `bookmark.go:9`,解析在 `parse.go:306` | "我存的那批视频" | 现在只有 `media_json <> '[]'`(`bookmark_repo.go:475`)这一层;类型要新列 |
| 多图 / 图集 | 同一个 JSON 数组的长度 | "四图帖" | 同上,一列 |
| Note Tweet vs 超过 280 字的长推 | `source_kind`(`bookmark.go:18`),解析在 `parse.go:205` | 真正的长文 vs 刚好过线 | 现成字段,面板加一行 |
| 赞数 ≥ N | `metrics_json`(`bookmark.go:44`,解析 `parse.go:355`) | "当初存下的高赞观点" | 排序已有(`savedview.go:15`),缺的是阈值 |
| 收藏 / 发布于某个区间 | `saved_at`、`created_at_on_x_ts`(`migrations.go:176`) | "上个月存的"、"两年前发布的" | 列与索引都在,只用于排序 |
| hashtag | `hashtags_json`(`migrations.go:257`),解析 `parse.go:254` | 作者自己写的公开话题 | 已经在驱动自动打标(`heuristics.go:124`),却不能拿来筛 |
| 还在不在 X 的书签里 | `last_seen_at`(`bookmark.go:72`),每次同步刷新(`display.go:360`) | "被取消收藏、作者删掉的那批" | 零新字段,与最近一次成功同步比较即可 |

技术上有一点要提前定:**`media_json` 和 `metrics_json` 是 JSON 列,SQL 里用 `LIKE` 判类型不可靠。**
仓库对同类问题已经有先例——`is_longform` 就是为了避开 SQLite `length()` 与规则不一致而新增的一列
加索引(`migrations.go:133`)。媒体类型与张数应该走同一条路,用 Go 回填。赞数阈值可以用
`json_extract`,但必须保住 `metrics` 用指针表达的那个区别(`bookmark.go:44`):**"没返回"不是 0**,
不能被阈值条件静默丢掉。

## 3. payload 里有、我们现在丢掉的

`parse.go` 从一条 tweet 里取五样东西:正文(`parse.go:203`)、媒体(`parse.go:285`)、
互动数(`parse.go:355`)、hashtag(`parse.go:254`)、发布时间原样(`parse.go:218`)。X 的 tweet
result 里还有这些,它们决定的正是"这条书签到底是什么":

| 字段 | 能筛出什么 | 注意 |
|---|---|---|
| `lang` | 只看中文 / 英文 / 日文 | 中文用户价值最高的一项;旧行无法回填 |
| `in_reply_to_status_id_str` | 独立观点 vs 某条 thread 里的一句话 | 书签里的回复离开上下文常常读不懂 |
| `is_quote_status` / `quoted_status_result` | 引用帖 | 同上 |
| `entities.urls` | 带链接 / 不带;按域名 facet | 域名是生态里最稳的一维,不需要用户维护 |
| `conversation_id_str` | 同一 thread 归组 | 这是分组,不是筛选 |
| `video_info.duration_millis` | 短视频 / 长视频 | 服务"待看"队列 |
| `card` | 文章 / 视频 / 投票 | 与媒体类型有重叠,优先级低 |

**核对方法,不要跳过:** 设置里打开「保存原始负载」(`settingsview.go:305`,解析侧是
`parse.go:21`),同步一页,读 `raw_payloads`(`migrations.go:268`)。这张表就是为核对这件事存在
的。上面的字段名来自 X 的 tweet result 结构,本文没有在本仓库里验证过它们仍然出现——**在写 schema
之前,用一页真实响应确认**。

回填的边界要写进设计:只有开过那个开关的行才有原始 JSON,其余的行永远拿不到语言和域名。所以这些
条件必须允许"未知"这一档,不能把老数据当成"非中文"或"无链接"。

## 4. 缺的是状态,不是数据

截图里灰掉的两项背后不是一个字段,是一次没做的产品闭环:

| 状态 | 需要什么 | 为什么值得 |
|---|---|---|
| 未读 / 已读 | 一列 `read_at`;打开详情即标记,加"全部标为已读" | 稍后读的主循环,是"阅读器"与"收藏夹"的分水岭 |
| 归档 | 一列 `archived_at`;移出主列表但保留可搜 | 让主列表只放还要处理的东西 |
| 星标 | 一列;详情与卡片各一个入口 | 可选,价值低于上面两项 |
| 上次同步之后新增 | 派生:`saved_at` 与最近一次成功同步比较 | 零存储,"今天新存了什么" |

**这两项不该是面板里的勾选框。** 面板回答"内容长什么样",未读与归档回答"我处理到哪一步"。后一组
的正确位置是 scope——和侧栏已有的"全部 / 收件箱 / 未归类"并列。混进面板会让同一屏出现两种语义的
开关,而勾选框本身也无法表达"这个状态是被我改过的"。

> **实施时的取舍(2026-11-15)**:侧栏刻意没有导航行(`sidebartabs.go:303`),除"全部 / 收件箱 /
> 某个列表"之外的 scope 只能从设置页进入,所以新加一个 scope 等于加一条没有入口的状态。于是:
> `read_at` 做成一条普通条件(`OnlyUnread`),能和媒体、长文叠加;`archived_at` 做成视图的模式
> (`Archived`),默认隐藏、勾上只看归档。两者都进了开关表 `filterFlags`,面板、chip、badge 和
> "全部清除"读同一份定义。打开详情即标记已读,列表的刷新推迟到详情关闭——否则"未读"筛选下,
> 读者刚打开的那一行会当场消失,详情跟着被关掉。
>
> **撤除(2026-11-15,验收后)**:上面这条 `read_at` 的假设被推翻了,半边实现当天撤掉,迁移 v6
> 删列。理由是它付不起自己的成本:状态在第一次打开详情时自动写入、不能标回,界面上只有
> "有圆点"和"没有圆点"两种样子——已读没有任何正向标志;一个装了 9,562 条、从没按"读过"整理
> 过的书库,每张卡片都有圆点,信号等于噪声。`archived_at` 留下:它改变列表里有什么。
> 要做一条真的待读队列,需要的是两向菜单、批量清空、计数与存量回填,那是另一套设计,不是在
> 自动标记上补两笔。

顺带一条已有的约束:书签被本机删除后进 `deleted_bookmarks`(`migrations.go:219`),那是同步的墓碑,
防止下次同步把它加回来。它与"已归档"不是一回事,不要复用。

## 5. 不建议加的

- **情感、主题、质量评分。** 需要每次同步跑模型,而且把"筛选"变成"猜测"。想要主题就去点标签,
  不确定的标签走建议(`suggestionsPanel`),由人确认——那条管线已经在,而且有失败与取消状态。
- **相似 / 重复内容。** 没有可靠数据,也没有判定标准。
- **作者认证、粉丝数阈值。** 书签是用户亲手存的,作者权威性在选择的那一刻已经表达过了。
- **有替代文本 / 无替代文本。** 数据现成(`parse.go:320`),但它回答不了"点下去之后我要做什么"。
  一个条件如果不能改变下一步,它只是数据库的投影。

判据只有一句:**这个条件点下去,用户接下来会做什么?** 媒体类型→去看那批视频;域名→去找那个项目;
未读→开始读。回答不了的就不加。

## 6. 面板,还是查询语法

再加五六个条件,262 宽的面板就摊不开了。两条路:

**A. 继续加 checkbox。** 发现性好,错误空间小;每一项都要一次点击、一次文案、一次翻译。

**B. 在现有搜索框里支持操作符。** `lang:zh`、`has:video`、`domain:github.com`、`likes:>100`、
`before:2026-01-01`。扩展性好,长尾不用进面板;代价是解析、错误提示和可发现性,而且搜索框现在的
语义是"子串匹配四个字段"(`libraryquery.go:73`),要动它就得先讲清楚哪些词是操作符。

倾向是混合:面板留六到八个常用条件,长尾走操作符,搜索框的空态里给一行提示。这也是大多数同类工具
最后停下来的形状——但它们都先把面板做对了。

## 7. 优先级与代价

**如果只做三件:**

1. **归档**(真实列 + 状态机 + 视图模式)。已做;曾一起做的未读同日撤除,见 §4 末尾。
2. **媒体类型。** 数据已在,一天;顺手把面板改成遍历开关表。
3. **域名 facet。** 生态里信息量最大的一维,要动解析器与回填策略。

再往后依次:语言、hashtag、赞数阈值、自定义时间区间。

**一个条件的落地清单**(以 `OnlyLongform` 为例,`grep -rl` 数到 18 个文件):

| 位置 | 要改什么 |
|---|---|
| `libraryquery.go:68` | 加字段、`Normalize`、`IsZero`、`ActiveCount` |
| `bookmark_repo.go:478` | 编译成 WHERE 子句 |
| `savedview.go:49` + `listsviews.go:119` | 存得进去、恢复得回来 |
| `importexport/dto.go:112`、`legacyformat.go:93` | 旧版导出的字段 |
| `state.go`、`reload.go` | 界面状态接到查询 |
| `filterfacets.go:85` | 一行,让 chip、徽标、"清除全部"都认识它 |
| `i18n.go` | 中英各一条文案 |
| 测试 | 领域、SQL、界面各一条 |
| `design.md` 的状态矩阵 | 一行期望与检查名 |

表里列的是"最小值",不是"全部"——facet counts、bundle 往返、命名检查可能还各要一处。这就是
"宁可少而准"的实际含义:一个条件不是一行代码,是一条穿过七层的线。
